# Deck Workflow

## 1. Lock the Communication Contract

Capture before research or layout:

- Audience and the decision or action sought
- Live presentation, send-ahead deck, application dossier, or mixed use
- Required language, file format, deadline, and confidentiality constraints
- Startup stage, funding target, intended runway, and next financing milestone
- User-supplied section order, slide counts, mandatory wording, and evaluation criteria
- Brand assets, product screenshots, reference decks, and visual preferences
- Available company facts, research, traction data, existing financials, and founder materials

Treat a screenshot or written outline as a content contract, not as a visual template. Preserve its requirements while improving the argument and design.

## 2. Build the Evidence Ledger

Create one internal row per material slide claim:

`Slide | Takeaway | Claim | Status | Source | As-of | Workbook range | Visual | Gap`

Use these statuses:

- `Provided`: supplied by the founder; not independently verified
- `Verified`: supported by a traceable primary or authoritative source
- `Estimate`: calculated from disclosed inputs
- `Assumption`: scenario input selected for modeling
- `Target`: future management objective
- `Missing`: required but unavailable

Prefer company records and primary sources. Use official statistics, regulators, filings, research owners, and competitor primary materials before aggregators. Current or unstable claims require current research. Do not treat two articles repeating the same upstream figure as independent corroboration.

## 3. Write Slide Contracts

Define each slide before layout:

`Headline | Evidence | Visual | On-slide copy | Speaker-note purpose | Sources | Workbook link`

- Keep visible copy concise and written for the audience.
- Use notes for explanation, caveats, methodology, and sources.
- Distinguish actuals from forecasts and targets visibly.
- Use exact timeframes with traction and growth metrics.
- Describe products through the user action and outcome, not a feature inventory.
- Connect the funding ask to runway, uses, and measurable milestones.

## 4. Write Clear, Focused Text

- Lead with the direct answer or conclusion. Arrange the rest in a clear, source-backed sequence such as chronology, cause -> effect, problem -> decision -> outcome, or claim -> evidence -> conclusion. Missing reason for a material transition -> STOP and request it.
- Keep one idea per paragraph. In slide copy, keep one idea per text block or bullet.
- Use concrete, sourced details. Every sentence must add a fact, explain a cause, clarify a choice, or advance the argument. Delete it otherwise, while preserving enough context for meaning, logic, and credibility.
- Use short sentences, familiar words, and minimal jargon. Keep the tone measured; remove hype, unsupported claims, promises, filler, and repetition.
- End each standalone answer or narrative with a grounded conclusion that completes its logic rather than repeating the opening or adding a slogan.
- When material, show each founder's distinct contribution and explain the practical reason for the chosen product focus.

## 5. Choose Visual Evidence

Use the visual form that matches the claim:

- Product behavior -> real screenshot, annotated flow, or before/after
- Trend or projection -> simple line or column chart
- Composition or unit economics -> stacked bars, bridge, or compact table
- Roadmap -> milestones with dates, dependencies, and proof criteria
- Team -> relevant accomplishments and founder-market fit

Use one dominant composition rather than a dashboard of interchangeable cards. Avoid generic startup imagery, gratuitous flags, decorative icons, fake device mockups, and diagrams that explain less than direct evidence.

## 6. Existing-Deck Route

When repairing a deck:

1. Inspect every slide and its notes.
2. Preserve the user's required order and the source deck's master/layout hierarchy.
3. Diagnose content, evidence, narrative, and visual problems separately.
4. Rebuild only the slides that fail the acceptance gates.
5. Apply revisions to the current deck in place. Create a separate revised copy and leave the current deck unchanged only when the user explicitly requests a new version.
